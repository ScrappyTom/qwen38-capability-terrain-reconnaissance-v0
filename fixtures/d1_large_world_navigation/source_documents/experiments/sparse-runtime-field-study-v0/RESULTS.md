# Sparse runtime field study v0 results

Status: **complete development field study; no runtime component promoted**

## Result

The study did not complete the maintenance task, but it exposed two important
errors in the proposed sparse operating method. The main systems finding is:

```text
sparse access does not create sparse cognition
```

After the transfer surface was mechanically corrected, Qwen3.8 adapted to the
byte cap and successfully used exact slices. It then used those slices to
rebuild the entire 51.7-KB target and the entire 37.9-KB orientation document
inside the ordinary transcript. It reached 25,970 prompt tokens before reading
any authoritative result report or changing the artifact. The cap changed the
transport unit; it did not give the model a discriminating reason to select a
small subset of the available world.

Second, the authentic task itself was selected from a stale date header rather
than the target's actual Git basis. The target had already been materially
updated on August 17. Only the later mechanical reentry-seed commit was new at
the pinned head. The intended broad semantic maintenance problem therefore did
not exist as stated.

The task-quality failure and the model-facing acquisition behavior are both
preserved. Neither is converted into a semantic model failure or into a claim
that Qwen cannot select from a useful map. This environment exposed paths and
bounded bytes, but not the target's trustworthy basis, the exact source delta
since that basis, or a structural address space for the target.

## Three development endpoints

| Run | Apparatus | Endpoint | Interpretation |
|---|---|---|---|
| r1 | unfiltered catalog; whole reads only | 4 actions, 33,712-token next request | invalid apparatus |
| r2 | filtered catalog; optional slices; unbounded literal lines | 5 actions, 38,185-token next request | invalid apparatus |
| r3 | 12-KB whole/slice cap; bounded exact search windows | 17 actions, 25,970-token next request | descriptive navigation endpoint only |

In r3, nine actions were accepted and eight were rejected while Qwen learned
the size/scoping contract. The nine accepted slices carried 89,569 bytes.
Across 17 successful inferences the run used 210,971 prompt tokens and 497
completion tokens. There was no mutation, check, or submission.

## What the bounded surface did and did not do

It did:

- prevent any one result from consuming the full context;
- preserve exact file/blob identity and slice coordinates;
- let Qwen recover mechanically from rejected oversized reads; and
- extend the trajectory from 4–5 actions to 17.

It did not:

- make Qwen use the project catalog, literal search, or path history;
- make Qwen select only decision-relevant document regions;
- prevent cumulative transcript growth;
- expose the actual delta between the target's last-changing commit and source
  head; or
- create headroom for authoritative evidence acquisition and editing.

The key distinction is:

```text
bounded result size
    ≠ bounded cumulative transcript
    ≠ selective working set
```

The model complied with the transfer mechanism while following a global
reacquisition strategy. Given a broad reconciliation task and no trustworthy
basis/delta/structure package, reading the maintained artifact and its
orientation entry point in full was a conservative response, not evidence of
a semantic inability to integrate evidence.

The field boundary separates four mechanisms that must not be collapsed:

| Mechanism | Question | What r3 established |
|---|---|---|
| Transfer | How much can one operation return? | mechanically bounded |
| Selection | Which exact regions should be acquired? | not induced |
| Residency | Which acquired bytes remain active? | ordinary transcript retained every accepted slice |
| Invalidation | Which prior material is no longer current? | no artifact-basis dependency was available |

This study solved only transfer. It primarily failed at selection and then
exposed the cumulative residency consequence.

## Cross-study qualification: the addressable unit matters

A separate Q3 XL study supplies an important cross-package counterpoint. Its
worlds exposed 14–18 separately addressable, decision-sized objects with stable
IDs, titles, kinds, versions, authority labels, abstracts, tags, and locators.
Across six research, writing, and coding tasks, Q3 XL made all six central
decisions correctly, passed 25/26 semantic criteria (one partial), made no
duplicate accepted read, and had no consequential acquisition or coverage
failure. Accepted breadth varied with the work: both research tasks read 13/14
objects, writing read 12/14 and 8/14, and coding read 6/14 and 5/14. See the
[pinned sister-study results](https://github.com/ScrappyTom/custody-cards-experimental-workbench/blob/3c651b66d1f991b686b4ddcaf9cc4fb3df55dfd4/studies/authentic-working-set-assembly-baseline-v1/reports/RESULTS.md).

That study used a different model package and does not repair or replicate this
trajectory. It does narrow the interpretation. Qwen-family behavior is not
well described as either “selective” or “exhaustive” in the abstract. The
field study exposed two large, internally heterogeneous files plus literal
byte ranges; slices changed transport without giving the model a useful basis
for deciding which internal regions mattered. The sister study exposed
meaningfully differentiated objects and the model assembled task-dependent
working sets from them.

The unit of addressability is therefore an experimental variable:

```text
repository → file → structural/semantic region → literal span
```

Working-set measurement must also separate:

- **breadth** — how many conceptual objects are acquired;
- **depth** — how much of each selected object is materialized; and
- **residency** — how much acquired material remains model-visible.

The objective is not the fewest reads. It is the smallest sufficient and
economical working set for the decision. A broad research synthesis may
legitimately need most conceptual objects, while a local code repair may need
only a few. Fixed source-count budgets are therefore not earned.

## Architecture consequence: incremental maintenance

The sparse architecture remains plausible, but generic random access is not
the missing primitive. Path lookup answers “where is an object?” It does not
answer the mechanical maintenance questions:

- what exact artifact version is my basis?
- what commits/objects changed after that basis?
- what structural regions exist inside this large object?
- where can I resume an exact bounded read without guessing its byte size?

Those are map/addressability problems, not semantic-summary problems. The
candidate operating pattern is closer to incremental computation:

```text
exact artifact basis
    → exact mechanical source delta
    → structural addressability
    → model-selected exact working set
    → exact action and receipt
    → new externally recorded basis
```

The host may state exact versions, changed commits/paths, hashes, and heading
or symbol ranges without deciding which change matters or what the artifact
should say. The model retains that semantic responsibility.

An editable artifact also cannot authoritatively declare its own currency. Its
content date is a model/user-authored field; its maintenance basis must be an
external custody record tied to exact source versions.

The stable harness remains unchanged. The repository provider stays removable
experimental apparatus.

## Methodology correction

Future authentic maintenance tasks must freeze:

1. the starting artifact blob and its last-changing commit;
2. the source head;
3. the literal commit/path delta between them; and
4. which task claims actually follow from that delta.

A date written inside an editable artifact is not a source-basis receipt.

Likewise, future “bounded working set” claims must report cumulative
model-visible bytes/tokens and actual tool adoption. An optional operation or
per-result cap cannot be described as the method unless the trajectory uses it
in a way that bounds active context.

## Disposition

Do not rerun the invalid broad “all evidence since August 15” task. The saved
target may be used once as a known development anchor only if the task is
corrected to the exact `e56769a1...` → `c700faab...` delta. It cannot provide
confirmatory evidence.

The next earned development comparison is:

- ordinary exact world plus bounded cursor reads; versus
- the same world and reads plus one mechanically generated package containing
  the exact artifact basis, complete source-head delta, and a target structure
  map whose sections have stable IDs, titles, exact ranges, hashes, and
  locators.

Neither arm should receive a summary, semantic relevance assignment, suggested
target section, checkpoint, or reviewer. The primary outcome is how much of
the available world must be materialized before a correct action; final
semantic quality and action headroom remain hard outcomes. Known stable region
IDs should be directly readable; query/search is for discovering identities,
not an admission prerequisite. Report conceptual breadth, per-object depth,
cumulative residency, duplicate/rejected reads, and which correctness-relevant
facts were already task-preloaded or mechanically preserved without reading.
If the package produces selective maintenance, validate it on a genuinely
fresh stale artifact. If Qwen still reconstructs every structural region,
only then is a residency or active-window mechanism earned. Do not tune slice
sizes on this fixture.

Cursor reads are common transport apparatus, not the main treatment. No index,
map, delta projection, or runtime policy is promoted by this development run.
